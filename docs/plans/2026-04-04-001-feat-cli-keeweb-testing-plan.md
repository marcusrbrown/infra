# feat: Add test infrastructure and coverage for CLI and KeeWeb

## Overview

Add the first test suite to the `@marcusrbrown/infra` monorepo. Wire Bun's built-in test runner into both `packages/cli` and `apps/keeweb`, add tests to CI, and cover the highest-risk surfaces: CLI command discovery, build pipeline correctness (SHA-256 verification, secret injection), deploy command flag validation, and status check logic.

## Problem Frame

The monorepo has zero test coverage — CI only runs lint + typecheck. CLI commands have irreversible operational effects (`keeweb deploy`), the build script handles secret injection and SHA-256 verification, and multiple AI agents contribute changes. Without tests, regressions in flag parsing, build correctness, and deploy preconditions are only caught in production. (see origin: docs/brainstorms/2026-04-04-cli-keeweb-testing-requirements.md)

## Requirements Trace

- R1. Test infrastructure: `bun test` scripts in `packages/cli` and `apps/keeweb`, wired into CI
- R2. CLI snapshot tests: `--help` outputs, command discovery, Zod validation errors
- R3. Build pipeline tests: mocked fetch, SHA-256 verification, secret injection, template integrity
- R4. Deploy command contract tests: flag validation matrix, preconditions, mocked Bun.spawn
- R5. Status command tests: HTTP health, content hash, last deploy — all with mocked externals

## Scope Boundaries

- No tests requiring network access, SSH, GitHub API tokens, or Docker
- No test framework beyond `bun:test` — no vitest, jest, or other runners
- No pre-commit test hook (CI-only for v1)
- No tests for `apps/cliproxy/` (PR #23 not merged)
- No deploy.sh bash testing — only TypeScript wrappers
- No MCP bridge testing — auto-generated by goke, low drift risk
- Tests must run in < 5 seconds total

## Context & Research

### Relevant Code and Patterns

- `apps/keeweb/src/build.ts` — 9 standalone async functions, not currently exported. `verifyArchiveHash`, `writeConfigWithSecret`, `ensureCachedArchive` are key test targets
- `packages/cli/src/commands/keeweb-status.ts` — exports `registerKeewebStatus`. Internal functions `checkHttpReachability`, `checkLastDeploy`, `checkContentHash`, `hashSha256` are not exported
- `packages/cli/src/commands/keeweb-deploy.ts` — exports `registerKeewebDeploy`. Internal functions `resolveDeployScriptPath`, `getLocalDeployEnv`, `validateLocalPreconditions`, `validateRemotePreconditions` are not exported
- `packages/cli/src/cli.ts` — goke CLI registration, imports command modules
- Bun test runner: `bun:test` module, `describe`/`it`/`expect`/`mock`/`spyOn`, `*.test.ts` convention, `toMatchSnapshot()`

### Institutional Learnings

- `docs/solutions/workflow-issues/bun-deploy-user-permissions-ci-2026-04-02.md` — deploy failures from permission drift. R4 deploy contract tests guard against regression of the conditions that caused these.

## Key Technical Decisions

- **Export testable functions with path parameterization where needed**: CLI command files (`keeweb-status.ts`, `keeweb-deploy.ts`) have no module-level filesystem side effects — adding `export` is sufficient. However, `build.ts` resolves paths at module scope via `path.resolve(import.meta.dir, '..')` — functions like `writeConfigWithSecret()` read/write from these hardcoded paths. For testability, add optional path-override parameters to build functions that touch the filesystem (e.g., `writeConfigWithSecret(overrides?: {configTemplatePath?: string, distConfigPath?: string})`). This avoids coupling tests to the real `dist/` and `config/` directories. `verifyArchiveHash(filePath)` already accepts a path param — no change needed.
- **Mock at boundaries using Bun-native patterns**: (a) Mock `fetch` by replacing `globalThis.fetch` in `beforeEach`/`afterEach` — Bun's `mock()` from `bun:test` creates callable mocks. (b) Mock `Bun.spawn` via `spyOn(Bun, 'spawn')` — returns a spy that can be `.mockImplementation()`'d to return controlled stdout/stderr ReadableStreams and exit codes. (c) Control `process.env` directly in tests (Bun supports mutation). Restore originals in `afterEach`.
- **Test file colocation**: `*.test.ts` files alongside source (e.g., `keeweb-status.test.ts` next to `keeweb-status.ts`)
- **Snapshot testing for CLI help**: goke produces deterministic plain-text help (no ANSI codes). Snapshots are stable across environments.
- **Minimal test fixture for build pipeline**: Small synthetic zip (a few KB) containing `index.html` and minimal structure — not the real 8MB KeeWeb archive. Generated once, committed to `apps/keeweb/src/__fixtures__/`. The fixture's SHA-256 is computed once and used in tests via the `expectedHash` override parameter — tests never reference the production `EXPECTED_SHA256` constant.
- **Per-package test scripts**: Each workspace package gets `"test": "bun test"`. Root `package.json` gets `"test": "bun test --recursive"` to run all workspace tests. CI adds `bun test --recursive` step.

## Open Questions

### Resolved During Planning

- **Can build.ts functions be tested in isolation?** Yes — functions are already separate. `verifyArchiveHash(filePath)` already takes a path param. Other filesystem-touching functions (`writeConfigWithSecret`, `ensureCachedArchive`, etc.) use module-level path constants resolved via `import.meta.dir`. Add optional path-override parameters to these functions for testability without coupling tests to the real `dist/`/`.cache/` directories.
- **Does goke help output include ANSI codes?** No — plain text. Snapshots will be stable.
- **Per-package or root-level test scripts?** Per-package `"test": "bun test"` + root `"test": "bun test --recursive"`.

### Deferred to Implementation

- Exact mock patterns for `Bun.spawn` — may need `mock.module()` or `spyOn()` depending on how commands import it
- Whether `build.ts` fixture zip needs to actually be a valid zip or just any file for SHA-256 verification tests
- Snapshot update workflow when intentional help text changes are made

## System-Wide Impact

- **Interaction graph:** Tests mock `fetch` and `Bun.spawn` globally within test files — ensure mocks are restored via `afterEach` or `beforeEach` cleanup to prevent cross-test contamination
- **Error propagation:** Test files that spawn CLI subprocess (`Bun.spawn`) must handle both stdout and stderr to avoid hanging processes
- **State lifecycle risks:** Build pipeline tests that write to temp dirs must clean up — use `afterAll` or Bun's temp file helpers
- **API surface parity:** CLI help snapshots serve as the command contract — update snapshots when intentionally changing command interfaces
- **Integration coverage:** Unit 7 integration run proves the full test suite works together

## Risks & Dependencies

- **Bun mock API stability**: `mock()` and `mock.module()` are relatively new in Bun. If mock behavior changes between Bun versions, tests may need adjustment. Mitigate: pin Bun version in CI via `oven-sh/setup-bun`.
- **Snapshot churn**: CLI help snapshots will need updating whenever command text changes. Low risk — intentional changes only.
- **Fixture maintenance**: The synthetic test zip is a one-time creation. If KeeWeb zip format changes, fixture needs updating. Very low risk — KeeWeb is frozen at v1.18.7.
