# apps/traces — trace collection stack

Collector, Langfuse, Tempo, Grafana and Prometheus for agent-run traces, on a dedicated DigitalOcean droplet at `traces.fro.bot`. A collector accepts OTLP over HTTP on that one public hostname, tells three sender groups apart by bearer token, limits each group by bytes, and sends every trace two ways: whole to Langfuse, and reduced to a named list of attributes to Tempo. Langfuse and Grafana have no public hostname; both are reached through an SSH tunnel. Ingest and a health path are the only public routes.

The decision record is `docs/plans/2026-11-20-001-feat-trace-collection-stack-plan.md`. This file covers the stack definition, the gated deploy and the health reporter. Provisioning is `server/provision.ts`; [`docs/runbooks/trace-collection.md`](../../docs/runbooks/trace-collection.md) is the operator runbook (health, deploy, ingest, sender tokens, backups, restore, rebuild); the CLI group (`traces status|logs|open|ingest|sender`) is in `packages/cli/src/commands/traces/`.

## Networks and exposure

| Network | Members |
| --- | --- |
| `edge` | Caddy, collector, Langfuse web, Tempo, Prometheus, health reporter |
| `backend` | Grafana, ClickHouse, PostgreSQL, Redis, MinIO, Langfuse web and worker, Tempo, Prometheus, health reporter |

Prometheus (`9090`) and the reporter's metrics listener (`8082`) are never published and Caddy never routes to them. Only Caddy publishes `80` and `443`. Langfuse web (`127.0.0.1:3000`) and Grafana (`127.0.0.1:3001`) publish to loopback for the SSH tunnel; keep the tunnel's local ports equal to these (Langfuse's `NEXTAUTH_URL` and Grafana's root URL are loopback URLs). No store port is ever published: Docker publishing bypasses the host firewall.

## Ingest

`https://traces.fro.bot/<group>/v1/traces` with `<group>` one of `marcusrbrown`, `fro-bot`, `workstation`. Each path reaches that group's collector receiver (ports 4411, 4412, 4413), which checks a token from `/etc/otelcol/tokens/<group>/token`. Caddy caps the body at 4.5 MiB; the collector caps the decompressed body at 8 MiB. A fourth receiver (4414) serves the deploy-time canary; Caddy never routes to it.

The ingest route has three states, chosen by `TRACES_INGEST_STATE` (unset means `off`) and read once when Caddy starts, so changing it recreates the Caddy container:

| State  | Ingest paths               | When                                             |
| ------ | -------------------------- | ------------------------------------------------ |
| `off`  | no route (404)             | first bring-up, or gates not yet passed          |
| `held` | 503, which senders retry   | a gated change is in progress, or `ingest hold`  |
| `open` | proxied to their receivers | every gate passed and ingest is meant to be open |

Timeouts: Caddy answers within 5 s (`read_header`), cuts a slow upload at 15 s, and gives a collector that does not acknowledge in 5 s a 504, because the sender abandons a request at 10 s.

## Collector

One receiver, one token file and one intake pipeline per group. The intake pipeline runs the byte limiter (`ratelimit`, bytes, 1 GiB allowance, 32 KiB/s refill; a full bucket answers 429), then stamps `sender.group` (upsert), then feeds two branches:

- **Langfuse**: the whole trace, no further processor, one persistent byte queue per group (1 GiB).
- **Tempo**: one shared pipeline through the `redaction` keep-list (structural keys only), one persistent queue (256 MiB).

The keep-list covers resource, scope, span and span-event attributes. It does **not** cover span link attributes, and span names, status messages and event names are not attributes, so they are kept. A new structural attribute is invisible in Grafana until it is added to `allowed_keys` in `config/otelcol.yaml`.

A 200 from the collector means queued, not stored by both backends. Delivery is at-least-once and the two backends can differ.

## Health reporter

`src/health-report.ts` runs in the `health-reporter` service (`oven/bun`, no install step, read-only root, Tempo's UID 10001, no Docker socket) and produces one verdict every five minutes: the collector, Tempo, both Langfuse services, Grafana, disk, and the age of the oldest data in each store. The periodic verdict sends no trace: it rests on the ready endpoints, the collector's exporter failure counters, queue fill and ingest 503s, Tempo's discard and truncation counters, disk space and data age. The canary is a separate mode of the same script, `bun run --no-install /app/health-report.ts --canary-once`. The deploy runs it once, by `docker compose exec -T health-reporter`, after the reporter's verdict is fresh, as a guarded step that holds the deploy step lock and checks ownership through the send and readback (`canaryScript` in `src/deploy.ts`). It sends one trace through the collector's private receiver, reads it back from both backends, prints the three canary checks as JSON followed by a sentinel line, and exits 0 whatever the checks say. A canary that throws or overruns the run deadline is three `unknown` checks. In Langfuse the canary is checked two ways: the markers Langfuse stores as fields must be in its ClickHouse row, and all nine must be in the raw batch that row names in the object store (Langfuse does not copy span links, generic span events or exception events into the row; `LANGFUSE_MARKER_LOCATIONS` is the one table to re-check on a Langfuse upgrade). In Tempo only the span name, status message, exception message and link attribute may survive, which is the keep-list check. Every probe has a timeout and each run a deadline, so one stuck dependency cannot stop later runs. It has three listeners:

- `0.0.0.0:8080` `GET /healthz`: `{ok, at}` and nothing else. Caddy routes this path publicly. `/metrics` is refused here.
- `127.0.0.1:8081` (the container's own loopback; nothing publishes it) `GET /detail` and `/live`. `traces status`, `traces ingest open` and the deploy read `/detail` with `docker compose exec -T health-reporter wget -q -O - http://127.0.0.1:8081/detail`, followed by a sentinel line.
- `0.0.0.0:8082` `GET /metrics` (the edge and backend networks; nothing publishes it and Caddy never routes it): the gauges below, in the Prometheus text format, from the reporter's latest finished run. A scrape reads the cache and never starts a probe. Before the first run the page is empty.

| Gauge | Labels | Meaning |
| --- | --- | --- |
| `traces_probe_up` | `target` = `langfuse-web`, `langfuse-worker`, `grafana` | 1 when the latest probe passed, 0 when not |
| `traces_disk_used_ratio` | `mount` = `volume`, `root` | used share from 0 to 1, as `df` computes it; the volume's is exported only while its sentinel is the recognised one |
| `traces_oldest_data_age_seconds` | `store` = `clickhouse`, `object-store`, `tempo` | seconds since the oldest data was written; absent for an empty or unreadable store |
| `traces_reporter_last_run_timestamp_seconds` | none | when the latest run finished; a run that overran its deadline leaves it, and the other gauges, as they were |

Every label is a fixed name and every value a number: nothing a probe read reaches the page. The checks are in two scopes, and `/detail` shows each check's `scope`:

| Scope | Checks | Read by |
| --- | --- | --- |
| `ingest` | `collector-*`, `tempo-*`, `langfuse-*`, `volume-space`, `root-space`, `data-age-*`, and any id nobody has classified (fail closed) | `ok`: the deploy's `reporter-verdict` gate and `traces ingest open` |
| `monitoring` | `grafana-health` (`GET http://grafana:3000/api/health`), `prometheus-health` (`GET http://prometheus:9090/-/ready`) | `monitoringOk`; never a gate and never `ok` |

`/detail` carries `ok` (the ingest verdict, fresh), `monitoringOk` (fresh) and `healthy` (`ok && monitoringOk`). `/healthz` answers `healthy`, so the external monitor still catches a dead Grafana or Prometheus, while a failure in either leaves `ok` passing: it can never refuse an `ingest open` or fail the deploy gate, and never makes a deploy hold an open route. The CLI reads `ok` as `isPassing` (ingest open) and `healthy` as `isHealthy` (`traces status`, which also prints the two verdicts apart); a reporter without the new fields reads as it did. The collector and Tempo verdict checks are unchanged and still decide `ok`; the alert rules below are a second, standard path for the same failures.

`/detail` also carries an `ingest` object (`null` when the metrics scrape fails or cannot be read): per group `acceptedSpans` and `refusedSpans` from the receiver counters, `requests` (HTTP status code to count for the three authenticated receivers, summed over label combinations, the canary route excluded) and a fixed `note`. All are totals since the collector started, not rates, and `refusedSpans` counts both 429 and 503. The 401 total includes the public monitor's unauthenticated probe every 15 minutes and the deploy-gate probes. The block is counts only and is never in `/healthz`; `traces status` prints it (text and `--json`), and the published CLI reads `/detail` as JSON with its own schema (it imports nothing from this app).

`collector-refused` fails only on a **503** from ingest: it means an exporter queue is full and the collector is shedding data. It reads `http_server_request_duration_count{http_response_status_code="503"}` summed over the series that are not the canary route (`/canary/v1/traces`), and applies the same rule as the other loss counters (first reading sets the baseline, any rise fails for 30 minutes). A **429** is the byte limiter working and never fails the verdict. `otelcol_receiver_refused_spans` is not used for the verdict because it rises for both. The three authenticated receivers export no `http_route` or `server_port`, so the 503 total cannot be split by group. An absent 503 series is zero, as for every counter that has never been incremented, but only while the request metric is exported at all: the check is `unknown` when the collector has accepted or refused spans and no `http_server_request_duration_count` series exists (a renamed or disabled metric), and `unknown` when the page is not the collector's or a value is not a count.

A verdict older than two intervals reads as failing. Two files carry the reporter's passwords, read on every run (so a change needs no restart): `secrets/reporter/clickhouse-password` (the read-only `traces_reader` user) and `secrets/reporter/minio-password`, both owned by UID 10001, mode 0400.

The reporter runs as Tempo's user on purpose. Tempo creates its data directories (`blocks`, `wal`, `live-store`) with mode 0700, so any other user gets "Permission denied" listing `blocks`, the Tempo age check reads `unknown (blocks-unreadable)`, and a check that is `unknown` fails the verdict, so ingest can never open. `TEMPO_USER_ID` in `src/host.ts` is that one id: the compose file's `health-reporter.user` and the owner deploy gives `secrets/reporter/*` both follow it, and `docker-compose.test.ts` pins both, and pins that Tempo has no `user` of its own. If a Tempo image bump changes the image's user, change the constant. The reporter mounts, all read-only: its source (`./health-reporter`, root-owned, 0644), `secrets/reporter` (its two files), `tempo_data` at `/var/tempo` (owned by 10001; the only mount owned by that user), the volume sentinel file and `/srv` (disk-fullness probes only). It mounts no token directory, no collector, Grafana or bootstrap secret, and no other store.

## Alerts

Ongoing failure alerting uses standard Prometheus metrics and alert rules. One Prometheus container (`prom/prometheus` on the 3.13 line, held there by a Renovate `allowedVersions` rule) scrapes four targets every 30 s: the collector (`otelcol`, `collector:8888`), Tempo (`tempo:3200`), the reporter (`health-reporter:8082`) and itself. It keeps 15 days or 2 GB. It evaluates no rules and has no Alertmanager, no `--web.enable-lifecycle`, no admin API and no remote-write receiver. Grafana queries it (data source uid `prometheus`, not the default) and owns the rules, which are provisioned from `config/grafana/alerting/` (mounted read-only) into one folder, `Traces stack`, in four groups. They post through one Grafana Discord contact point (`traces-discord`), whose URL is `$TRACES_DISCORD_WEBHOOK_URL`. That variable is a deploy secret, written to the host `.env` and passed to Grafana only (`${TRACES_DISCORD_WEBHOOK_URL:?}`, so a stack without it does not start). The one policy sends every alert to that contact point: grouped by folder and alert name, `group_wait` 30 s, `group_interval` 5 m, `repeat_interval` 4 h, resolutions sent.

| Rule | Group | Fires when | Severity | No data | Query error |
| --- | --- | --- | --- | --- | --- |
| `TracesTargetDown` | stack | `up == 0`, 5 m | critical | Alerting | Alerting |
| `LangfuseDown` | stack | `traces_probe_up` of `langfuse-web` or `-worker` is 0, 5 m | critical | OK | KeepLast |
| `GrafanaDown` | stack | `traces_probe_up{target="grafana"}` is 0, 5 m | critical | OK | KeepLast |
| `ReporterStale` | stack | the last run finished over 15 m ago, 5 m | warning | Alerting | KeepLast |
| `CollectorQueueFilling` | collector | queue size over capacity is 0.8 or more, per exporter, 5 m | warning | OK | KeepLast |
| `CollectorExportFailures` | collector | send or enqueue failed spans rose in 30 m, per exporter | critical | OK | KeepLast |
| `IngestRefused503` | collector | ingest answered 503 in 30 m, canary route excluded (`http_route=""`) | critical | OK | KeepLast |
| `TempoDiscards` | tempo | spans discarded in 30 m | critical | OK | KeepLast |
| `TempoAttributeTruncation` | tempo | attributes truncated in 30 m | info | OK | KeepLast |
| `VolumeSpaceWarning` / `VolumeSpaceCritical` | storage | volume used share 0.70 or more (10 m) / 0.85 or more (5 m) | warning / critical | OK | KeepLast |
| `RootSpace` | storage | root used share 0.85 or more, 10 m | critical | OK | KeepLast |
| `DataOlderThan31d` | storage | a store's oldest data is over 31 days, 10 m | critical | OK | KeepLast |

**Absence is decided per rule.** The loss counters (`otelcol_exporter_send_failed_spans`, `..._enqueue_failed_spans`, Tempo's discard and truncation counters) are not exported until their first increment, so no data means no loss and never alerts (`noDataState: OK`); `increase()` of a series that is absent, then 1, then flat is 0, so each loss query is two halves joined by `or`: `increase(x[30m]) > 0` for a series that was there and rose, and `sum(x unless x offset 30m) > 0 and on() (up{job="…"} offset 30m == 1)` for a series that is present now and was absent 30 minutes ago. The guard means monitoring start-up, or a target that was down 30 minutes ago, does not page on an old count; the cost is that a counter that first appears with less than 30 minutes of history is not alerted. Export failures join their two counters with `or` over a `kind` label (`label_replace`), never a `+` between two vectors (which drops every series missing from one side) and never one name regex (`increase` drops the metric name, so two counters of one exporter collide and the query errors). `config/prometheus/loss-rules.yml` mirrors the four queries and `loss-rules.test.yml` holds the promtool cases (never present, absent then positive then flat, a positive baseline at start-up, a normal increase, the canary route excluded). Neither file is loaded by Prometheus or uploaded by deploy; `config/prometheus/loss-rules.test.ts` fails when a mirror query differs from the Grafana rule, and runs `promtool test rules` in the pinned image with `--network none` when docker and the image are already present (it skips otherwise, and never pulls). `TracesTargetDown` and `ReporterStale` read series that must always exist, so no data means the monitoring is blind and alerts; `TracesTargetDown` also alerts on a failing query. A query that fails keeps every other rule's last state, so a Prometheus outage neither resolves a firing alert nor starts new ones; the outage itself is caught by `prometheus-health` through `/healthz` and by `TracesTargetDown`. The thresholds are the reporter's (`THRESHOLDS`), and a test pins them. The rule `uid`s are fixed (`traces-*`), so a silence or a mute timing made in the Grafana UI stays attached across deploys.

Message templates are fixed text, the rule's own label values (`exporter`, `job`, `instance`, `target`, `mount`, `store`, `reason`) and numbers. A test rejects any other template variable. The webhook address is in no tracked file.

The deploy checks the result in its second operator gate (below). Silencing and the rest of the day-2 procedure are in the runbook.

## Deploy

`bun run deploy:traces` (root wrapper; loads the root `.env`) or the `deploy-traces` workflow. The inputs are exactly `TRACES_DEPLOY_SECRETS`, `TRACES_DEPLOY_VARS` (`TRACES_DOMAIN`, `TRACES_INGEST_OPEN`) and `TRACES_DEPLOY_BUILD_INPUTS` (`TRACES_COLLECTOR_IMAGE`, from the workflow's build job) in `src/deploy.ts`; a conventions test compares them with the workflow. A sender token, the snapshot token and the DigitalOcean token are never read.

The workflow builds the collector image without a provenance attestation, on purpose. The build is reproducible, and an attestation differs on every run, so with one attached the pushed digest changed for an unchanged image and every deploy restarted the collector (and would hold an open route to do it). The digest now changes only when the image does.

Order: validate every input; DNS preflight; verify the volume mount, sentinel and storage paths (`checkTracesStorage`, fail closed); under the step lock (waiting for any other deploy's step in flight) and then the ingest lock, read the host's state and write the deploy marker (carrying this deploy's id) in one script; compare every file with the host and, on an open route, compare the running services with the files; hold the route if it is open and a gated service is about to change or is not running what the files say; write directories, deny-all token files where none exists, secret files, configs and the reporter source; prune images, check free space, pull; create the collector container and fix its queue volume's owner; start the stores and Langfuse; assert and read back retention; start Tempo, Grafana and the collector; restart the reporter; verify the collector's running image digest; start Caddy; run the gates; set the route; start Prometheus; remove the deploy marker; check Grafana's sign-in and its provisioned alerting (read-only, after the route is final).

Everything goes over one multiplexed SSH connection with pinned host keys (`StrictHostKeyChecking=yes`). The ssh child's environment is `PATH`, `HOME` and `SSH_AUTH_SOCK` and nothing else; a secret reaches the host on stdin only, written to a temporary file in the destination directory with its owner and mode set first, then renamed over the target.

The CLI follows the same rule. The host rate-limits new SSH connections (`ufw limit 22/tcp`: six from one source within 30 seconds refuses the next for about 30 seconds), so every multi-step `infra traces` command (`status`, `ingest hold|open|status`, `sender add|list|revoke`) uses one multiplexed connection (`withRemoteSession` in `packages/cli/src/commands/traces/remote.ts`). `traces open` and `traces logs` are single long-lived connections and use a plain one.

"Differs" means the content, the owner or the mode: `compareFileScript` reads the file's numeric `uid:gid` and mode (`stat -c '%u:%g %a'`, GNU coreutils, which the host has) as well as its bytes, so a file whose content is unchanged but whose owner changed (the reporter's secrets, when the reporter's user changed) is rewritten through the same write-then-rename path, and the services that mount it are recreated as for a content change. A host that cannot answer `stat` fails the step; it is never read as "same". Token files are the exception and are never compared.

| File | Owner and mode | Written when |
| --- | --- | --- |
| `.env` | root, 0600 | content (without the ingest-state line) differs; the state line is appended on the host |
| `secrets/collector/langfuse-basic` | root:65532, 0440 | differs. `base64(public:secret)`, no trailing newline; a placeholder the collector can start with and Langfuse refuses when the key pair is unset |
| `secrets/grafana/{admin-password,secret-key}` | 472:472, 0400 (directory `root:472`, 0750) | differs |
| `secrets/reporter/{clickhouse-password,minio-password}` | 10001:10001, 0400 | differs |
| `config/**`, `docker-compose.yaml` | root, 0644 | differs. `config/prometheus/prometheus.yml` recreates Prometheus; `config/grafana/{datasources,alerting}/**` recreate Grafana |
| `health-reporter/health-report.ts` | root, 0644 | differs. Mounted read-only at `/app` |
| `tokens/<group>/token` | root:65532, 0640 | **never**, once it exists. Created with one void line only when absent (a temporary file hard-linked into place, which fails if the target exists) |

A changed config file recreates only the service that mounts it; compose recreates what a changed image or environment touches. The collector's queue volume is root-owned when Docker creates it, so deploy creates the container, sets the volume directory's owner to 65532 (only a path under Docker's data root on the volume) and reads it back, instead of relying on Docker copying ownership from the image (the host keeps images in the containerd store, where that copy is the least-tested path).

### The deploy marker and the locks

`/mnt/traces/app/.deploy-in-progress` (`TRACES_DEPLOY_MARKER` in `src/host.ts`) is a regular file with one line, `<deploy id> <UTC timestamp>`. The deploy id is 16 random bytes as hex, made on the machine that runs the deploy. Deploy writes the marker in its first host script, under the step lock and the ingest lock and together with the read of the route state, so a manual open has either finished before that read or is refused after it. Deploy removes it as the very last step of a deploy that evaluated every gate and left the route in its final state, including the legitimate "completed with ingest off because the key pair is unset" outcome. Any other throw leaves it, and the next deploy overwrites it: a marker never blocks a deploy from starting. While the file, or `.pending-restarts`, exists, `traces ingest open` refuses (the CLI tests only that the file exists, not what it holds); holding never is refused. A leftover marker on an open route makes the next deploy hold first.

**The last deploy to start owns the host.** A deploy is many separate SSH commands, so no lock can span the whole deploy (`flock` ends with each command), and none does. Ownership spans it, and a per-step lock makes ownership hold for the whole of each step. Every script of a deploy that changes the host (file writes, `.env`, the pending-restart and bootstrap records, directories, token-file creation, image prune and pull, compose create and up, the queue volume, the retention `ALTER` and lifecycle statements, every hold and open, and the marker removal) begins with the same prelude, `ownershipPrelude` in `src/deploy.ts`: it takes `flock` on the step lock (`TRACES_DEPLOY_STEP_LOCK`, descriptor 8, up to 60 s) and keeps it until the script's shell exits, then checks that the marker exists and its first field is this deploy's id. Otherwise the script prints `DEPLOY_OVERTAKEN`, exits non-zero and has changed nothing. The open, the hold, the `.env` rewrite and the marker removal run that check in the same script as the write, then take the ingest lock (lock order is always step lock, then ingest lock); the step lock keeps the check true until the script ends, so nothing falls between check and act; the marker is removed by compare-and-delete. A test enumerates every script builder and fails for a mutating one without the check; read-only probes carry none. A deploy that is refused throws `DeployOvertakenError` ("another deploy started on this host and took over; this one stopped without opening ingest") and is the one failure path that deliberately leaves the route and the marker alone: it does not hold, probe or remove anything, because the host now belongs to the newer deploy. The takeover (`beginDeployScript`) takes the same step lock before it writes the marker, waiting up to 15 minutes (`TAKEOVER_LOCK_WAIT_SECONDS`, 900 s: a step can be an image pull or a service start). What this guarantees: from the moment a deploy owns the host, no other deploy's step is running or can start. A step of an older deploy that passed its check (a `compose up` in flight, say) finishes before the newer deploy's takeover completes, so the newer deploy's gates never run beside it and the older deploy's next step is refused as overtaken; only the newest deploy can open ingest or clear the marker. A takeover that cannot get the lock in 15 minutes prints `DEPLOY_STEP_BUSY`, changes nothing and fails with `DeployStepBusyError` (another deploy's step is still running; retry when it finishes); an ordinary step that cannot get it in 60 s (it only ever contends with a takeover) fails the same way and goes through normal failure handling. What it does not do: stop a person starting a second deploy, which only wastes time (see the anti-pattern below), or interrupt an in-flight step. Read-only probes take neither lock, and the manual `traces ingest hold|open` commands take only the ingest lock, so an emergency hold never waits on a deploy step: no deploy script holds the ingest lock across a pull, a start or any long operation, only across the state read and write and the Caddy recreate.

Every ingest state change deploy makes runs inside `flock -w 30` on `/mnt/traces/app/.ingest.lock` (`TRACES_INGEST_LOCK`), taken before the state is read and held through the Caddy recreate. A lock not taken in 30 s prints `LOCK_BUSY` and fails; it is never skipped. When deploy replaces `.env` it re-reads the state line under the same lock and writes the less open of that and its own plan, so a manual `traces ingest hold` made during a deploy survives; only the gated open step opens. The step lock (`/mnt/traces/app/.deploy-step.lock`, `TRACES_DEPLOY_STEP_LOCK`, descriptor 8) is deploy-only and is always taken before the ingest lock in a script that takes both. A lock not taken in time prints its own sentinel (`DEPLOY_STEP_BUSY`) and fails; it is never skipped. The token files have their own lock (`TRACES_TOKENS_LOCK`), used by the sender-token commands only.

### Holding, gates and the route

A gated service is the collector, a backend (Langfuse, ClickHouse, MinIO, Redis, PostgreSQL, Tempo) or Caddy, and the compose file or `.env` count as changes to them. A file comparison alone cannot see that `compose up` would start a stopped gated service or recreate one whose container no longer matches the files, so on an open route whose files are all unchanged the deploy also compares each gated service's running container with the files: it must exist, be running, and carry a `com.docker.compose.config-hash` label equal to `docker compose config --hash <service>`. When the files are unchanged, the files on disk are the ones `up` will read, so this comparison needs no staging. Any difference, and any answer that cannot be trusted (failed command, missing service, unknown word), counts as a change. On an open route, a deploy that is about to change a gated service holds the route first (the same on-host command as `traces ingest hold`: the state line in `.env`, then `up -d --force-recreate --no-deps caddy`) and proves 503 on all three paths from inside the host before anything else changes. A deploy that changes nothing gated does not hold. If the hold cannot be proven, the deploy stops with nothing changed. Restarts a failed deploy left undone are recorded in `.pending-restarts` before any file is written, so the next deploy acts on them even though every file now matches, and treats them as a change.

After any failure past the marker, except being overtaken (see "The last deploy to start owns the host"), the deploy does not trust what it last wrote. It reads the route from the host (`.env`'s state line, and one probe of what Caddy actually answers) and accepts it only if it is positively off or held with Caddy answering as that state does (a host with no `.env` runs nothing and counts as off). Anything else, including a state change whose reply was lost after the host acted and a route another operator opened meanwhile, is held and proven 503. If that cannot be done the error says plainly that ingest may be open and names `traces ingest hold`.

After the stack is up the deploy evaluates the gates (`evaluateGates`; every gate has a failing test):

| Gate | Passes when |
| --- | --- |
| `langfuse-key` (config) | the Application-role key pair is set |
| `ingest-variable` (config) | `TRACES_INGEST_OPEN` is exactly `true` |
| `retention` | the TTLs and the lifecycle rules were asserted and read back |
| `token-directories` | every group has a token file that is not empty (a deny-all file passes; a missing or empty one fails) |
| `reporter-verdict` | a verdict produced after the reporter restart is fresh and passing |
| `canary` | the deploy's one canary: `canary-send`, `canary-langfuse` and `canary-tempo` each pass. It runs only when the reporter's verdict is fresh; if it cannot be run or read, the gate fails. The canary span carries `langfuse.environment=canary` (`CANARY_ENVIRONMENT`), so it lands in its own Langfuse environment and can be filtered out; the readback finds its row by `trace_id` and never filters on environment |
| `bootstrap-key` | the bootstrap pair is not supplied, and Langfuse answers 401 to it (or no pair is on record) |
| `bootstrap-variables` | no `LANGFUSE_INIT_PROJECT_*KEY` has a value in the host `.env` or in any running container |
| `grafana-signin` (operator) | after the route is final, on the host, `GET http://127.0.0.1:3001/api/user` answers 200 to `admin` with the password in `secrets/grafana/admin-password` |
| `grafana-alerting` (operator) | after `grafana-signin` passes, on the host, Grafana's provisioning API lists the contact point `traces-discord` with type `discord` and every rule group in `ALERT_RULE_GROUPS` with the rule count its file defines. Two `GET`s with the same credential handling; no test notification, no write |
| `prometheus-ready` (operator) | after the route is set, the Prometheus container was created, its data volume was given to 65534 and read back, and `up --wait` found it healthy. Guarded steps; a failure fails the run and never touches the route |

`grafana-signin`, `grafana-alerting` and `prometheus-ready` are a third kind of gate, `operator`, and none is part of `evaluateGates`. Grafana is an operator UI behind the SSH tunnel and has nothing to do with whether traces can be received, so nothing Grafana does may hold, close, open or keep closed the ingest route, or add to the time the route takes. `runDeploy` decides and verifies the route from the route gates alone, removes the deploy marker and returns; only then does `performDeploy` run the Grafana check (`awaitGrafanaSignIn`, over the bare SSH `exec`, never inside `runDeploy`'s failure handler, which would close the route). Every outcome of the check (a 200, a refusal, a timeout, a rejected execution, malformed output) is reported as `OperatorSurfaceError`, which fails the run, names the HTTP code or the cause, and says where the route is; none of them can reach the route. A deploy that already failed never runs the check. `grafanaSignInScript` reads the password from the file on the host and hands it to curl as a config on stdin (`-K -`); the password is in no argv, no SSH command text and no log line, and only the status code is printed (tests run the script for real with a recording curl). It runs `curl -q --noproxy '*'` (`-q` only works as the first argument), so a `.curlrc` or a proxy variable on the host cannot take the request off loopback. It sends one request and none with `admin:admin`: Grafana counts failed Basic Auth logins per username (5 in 5 minutes), so a second request would spend a failed login on the admin account at every deploy. One 200 with the file's password proves the account holds the file's value, and `GRAFANA_ADMIN_PASSWORD_MIN` (16 characters, checked in `readInputs` before any SSH) keeps that value from being Grafana's default, `admin`. It retries only while Grafana has not answered (`000` or 5xx, up to `grafanaAttempts` x `grafanaIntervalMs`); a settled 2xx to 4xx is final, so a wrong password is not tried repeatedly.

`grafana-alerting` proves Grafana read and accepted the provisioning files (it refuses a file it cannot parse, and a contact point needs a valid webhook address); it cannot prove a message reaches Discord, because it sends none. It runs only after the sign-in check passed: one refused password is already a failed login, and a second request would spend another. It cuts every contact point's `settings` out on the host, so the webhook address (which Grafana also redacts) is in no output, and it makes one attempt, with no retry.

Prometheus runs as `65534:65534` (`PROMETHEUS_USER_ID` in `src/host.ts`; `nobody`, the user its image declares), on a read-only root with no capabilities. Its data volume `traces_prometheus_data` is root-owned when Docker creates it, so deploy creates the container, sets the volume directory's owner to 65534 (only a path under Docker's data root) and reads it back (`prometheusVolumeScript`), as for the collector's queue. Prometheus is **not gated**: it is on no trace's path and holds no trace content. For the same reason it is started after the route is decided and not in the route-critical `up --wait` steps: `create-prometheus`, `prometheus-volume` and `up-prometheus` (guarded like every host change, force-recreated on every deploy as the reporter is, so a changed `prometheus.yml` needs no pending-restart record) run after the route is final and before the marker is removed. A failure there is the `operator` gate `prometheus-ready`: the run fails (`OperatorSurfaceError`, which says the route was not changed) and the route is never held, closed or kept closed. It is not run when a safety gate failed. `traces status` and the reporter's `prometheus-health` then say whether it is up. Its healthcheck is `wget --spider` on `/-/healthy`, which the image's busybox has.

Grafana runs as `472:472` (`user: '472:472'` in the compose file; `GRAFANA_USER_ID` in `src/host.ts` is the one id, and `docker-compose.test.ts` pins it). The image's own user is 472 with group 0, and deploy makes `secrets/grafana` `root:472`, mode 0750, so a process whose group is 0 cannot enter the directory: Grafana logged `cat: can't open '/run/secrets/grafana/admin-password': Permission denied` for both files and started on its defaults (admin password `admin`, the built-in secret key). Grafana applies the admin password only when it creates its database, so after this fix an existing Grafana volume keeps whatever password it was created with; see the runbook's "Grafana sign-in check fails".

The route opens only if every route gate passes. With no key pair, everything that needs a delivering stack is skipped, the route stays `off` (or is held if it was open) and the deploy completes saying which gates are missing. With the key pair set, any failing safety gate fails the deploy: an open route is held first, and the error is `AppliedButUnverifiedError`, which says the host was updated and not verified, and whether ingest is held, off, or could not be confirmed closed. Every failure after the deploy takes its marker goes through that one handler, the file-comparison phase included: a comparison that cannot be trusted (a lost SSH reply, a host whose `stat` fails) holds an open route and proves it, or says the route could not be confirmed closed and to run `traces ingest hold`. Because nothing was written, that error is `FilesNotComparedError`, not `AppliedButUnverifiedError`: it says the files could not be compared, that nothing was updated, where the route is, and that the marker stays so the next deploy holds first. `DeployOvertakenError` still bypasses the handler (no hold, probe or removal), and so does a busy step lock reported during the comparison. After opening, the deploy proves 401 on all three paths from inside the host (`curl --resolve`, the real certificate and route) and holds again if it cannot.

### Retention

`src/retention.ts` asserts on every deploy: a 30-day TTL (`toDateTime(start_time) + INTERVAL 30 DAY`) on `events_full` and `events_core` (required; Langfuse creates them, so missing is "not ready" and retried, then a failure that names them), and on `traces`, `observations`, `observations_pid_tid_sorting` and `scores` where they exist; and 30-day lifecycle rules on the object store's `events/` (every OTLP batch, kept until something deletes it) and `media/` (attachments Langfuse extracts from trace content, so content can sit there) prefixes. A rule already on a prefix that is not a 30-day expiry is a conflict, not something the deploy edits. Everything is read back; no `ALTER` runs when a TTL already matches. The TTL is read from the table's `CREATE` text by a small scanner (`extractTtl`): only a `TTL` outside every parenthesis counts (a column's TTL does not), and nothing inside a single-quoted string or a backtick identifier does (a `COMMENT` can say anything).

### The first deploys

1. **Deploy 1**: store and Langfuse-user secrets, the bootstrap pair, no key pair, `TRACES_INGEST_OPEN` unset. Stack up, retention asserted, `ingest off`, a message that the key pair is not set. Langfuse creates the organisation, project, user and the full-access bootstrap key from `LANGFUSE_INIT_*`.
2. Operator: open the tunnel, create the Application-role key in the Langfuse UI, delete the bootstrap key there, set `TRACES_LANGFUSE_PUBLIC_KEY`/`SECRET_KEY`, delete the `TRACES_LANGFUSE_BOOTSTRAP_*` secrets, publish the privacy page, set `TRACES_INGEST_OPEN=true`.
3. **Deploy 2**: `.env` is rewritten without the bootstrap key variables and Langfuse web is recreated; the pair that was in the old `.env` is set aside in `secrets/bootstrap-pending` (root, 0400, mounted nowhere) and used to probe Langfuse. 401: the key is dead, the record is removed, and if every other gate passes the route opens. 200: the deploy fails with ingest off and says to delete the key in the UI; **deploy 3** (any run, same inputs) probes the record again.
4. Sender tokens are issued afterwards, with `traces sender add`.

### Langfuse `LANGFUSE_INIT_*` at v4.83.0

`web/src/initialize.ts` at the `v4.83.0` tag: the organisation and the project are `upsert`s with `update: {}`; the user is created only when no user with that email exists, so a later boot never resets the password and rotating `TRACES_LANGFUSE_USER_PASSWORD` changes nothing after the first boot; the organisation membership is re-asserted as `OWNER`. The API key is created only when `LANGFUSE_INIT_PROJECT_ID`, `..._PUBLIC_KEY` and `..._SECRET_KEY` are all set and no key with that public key exists, so **a key deleted in the UI comes back on the next boot while the key variables are present**, as a `LEGACY_PROJECT_API_KEY` with full access. With the two key variables absent and the organisation, project and user variables still set, a boot creates no key and changes no password. That is the design: the key variables are written only when the bootstrap pair is supplied, never otherwise.

## Secrets and tokens

Nothing secret is in a tracked file. The stack reads `.env` from the app directory (`POSTGRES_PASSWORD`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_READER_PASSWORD`, `MINIO_ROOT_PASSWORD`, `REDIS_AUTH`, `SALT`, `ENCRYPTION_KEY`, `NEXTAUTH_SECRET`, `TRACES_DOMAIN`, `TRACES_COLLECTOR_IMAGE`, `TRACES_INGEST_STATE`, and the `LANGFUSE_INIT_*` bootstrap values), and files from directories mounted read-only, owned as the table under "Deploy" says. Passwords go inside connection URLs, so each is URL-safe (letters, digits, `. _ ~ -`) and at least 24 characters; the encryption key is 64 hex.

The collector runs as UID 65532. Its token directories must be readable and its queue volume writable by that user. Sender tokens belong to the operator command (`traces sender`); a token file it replaces keeps `root:65532` and mode 0640.

### Token files

A token file is never empty. Measured against the pinned collector image: replacing a live token file with an empty one left the old token accepted; replacing it with a different line revoked the old token in about a tenth of a second; and a collector started with an empty or missing token file starts, answers 401 to everything, and does not notice a token added later until it is restarted (the credential watcher in `extension/internal/credentialsfile/filewatcher.go` at v0.165.0 rejects an empty file and is not registered when the first read fails).

So "no tokens" is one **void line**: `trc_void_<43 base64url characters> void <timestamp>` (`TRACES_VOID_TOKEN_PREFIX` in `src/host.ts`), a token generated on the operator's machine, sent on stdin and kept nowhere. A real token is any line whose first field does not start with that prefix. Deploy creates a missing file as one void line. `traces sender revoke` of a group's last real token and `revoke --all` write a fresh void line. `list` hides void lines. Provisioning's `--reopen-ports` refuses while any group has a real token and faults on a missing or empty file. If a file is ever found empty, write a void line (`traces sender revoke --all` does) and restart the collector.

## Anti-patterns

- **Never publish a store port.** ClickHouse, PostgreSQL, Redis, MinIO, Tempo and Prometheus stay off the host. Only Caddy, Langfuse web (loopback) and Grafana (loopback) have a `ports` entry; a test enforces it.
- **Never route `/metrics`, `8082` or Prometheus through Caddy, and never add `/metrics` to the public `8080` listener.** A test refuses it on `8080` and in every Caddy state.
- **Never turn on Prometheus's lifecycle endpoint, admin API or remote-write receiver, and never add Alertmanager or rule files.** The rules are Grafana's; a test pins the flags.
- **Never put the Discord webhook address in a tracked file, an argv or a log, and never give it to a service but Grafana.** It travels in the host `.env` and Grafana's environment; the contact point reads `$TRACES_DISCORD_WEBHOOK_URL`.
- **Never make an alert message read trace content.** A message is fixed text, the rule's own labels and numbers; a test rejects any other template variable.
- **Never add a processor to the Langfuse branch.** Langfuse gets the whole trace. A processor there (`batch`, `transform`, anything) changes what is stored. No `batch` or `transform` processor anywhere.
- **Never put a content key in the keep-list.** The six `gen_ai` content keys stay out; a test enforces it.
- **Never copy a token off the host, and never let deploy touch one.** Sender tokens live in `tokens/` on the encrypted volume and at the senders; `list` shows fingerprints only. Deploy creates a file with one void line when none exists and never writes, replaces, truncates or removes an existing one.
- **Never pass a secret on a command line.** Secret bytes go over SSH stdin; the SSH argv and the SSH child's environment carry none, and the remote scripts read passwords from the container's own environment.
- **Never write the `LANGFUSE_INIT_PROJECT_*KEY` variables unless the bootstrap pair is being supplied.** Langfuse recreates a deleted key from them on the next boot.
- **Never open the route without every gate.** Open means all gates pass and `TRACES_INGEST_OPEN` is exactly `true`; `mayOpen` is the only decision and a skipped gate is not a pass.
- **Never change a gated service on an open route without holding it first.** The hold comes before the first write to the stack, and a service that is stopped or drifted from its files counts as a change.
- **Never trust the deploy's own record of the route after a failure.** Read it from the host; a lost reply and a concurrent `traces ingest open` both leave it different from what the deploy wrote.
- **Never remove the deploy marker on any path but a completed deploy, and never remove one that holds another deploy's id.** A failed or interrupted deploy leaves it; that is what keeps `traces ingest open` refused. Removal is compare-and-delete under the ingest lock.
- **Never run two deploys at once.** `traces deploy --local` during the workflow's run is not covered by the Actions concurrency group. It is wasteful, not unsafe: the second deploy waits (up to 15 minutes) for the first's step in flight, then takes the host, and the first is stopped at its next step. Wait for the workflow run, or cancel it, before deploying locally.
- **Never add a script that changes the host without the ownership check.** Build it with `guardedStep`, `composeStep` or `ownershipPrelude` (which carries the step lock) and classify it in the enumeration test; a retention-style script from another module takes the check as a parameter.
- **Never `docker compose down -v`.** The volumes hold the traces. Deploy only ever runs `up -d` (and `create --no-recreate` for the collector container).
- **Never cap ClickHouse memory.** Capping it near 7 GB made the Langfuse worker drop rows after the sender got 200.
- **Never add a compose healthcheck to the collector or Tempo.** Both are distroless images with no shell; the health reporter probes them.
- **Never leave `TRACES_INGEST_STATE=open` unless every gate has passed.**
- **Never empty a token file.** The collector keeps the old tokens, and a file that is empty at start is never watched. Write a void line.
- **Never read the route state or write the deploy marker outside the ingest lock, and never take the ingest lock before the step lock.** The takeover and every mutating script take the step lock first.
- **Never make a manual command (`traces ingest hold|open`) take the step lock, and never hold the ingest lock across a long deploy operation.** Either would make an emergency hold wait on a deploy step.
- **Never regenerate a long-lived secret** (`SALT`, `ENCRYPTION_KEY`, `NEXTAUTH_SECRET`, store passwords). A volume holds data keyed to them; deploy never generates one.
- **No remote command redirects to the null device or deletes outside the app directory and `/tmp`**, and every probe prints a sentinel and needs exit 0 plus a recognised sentinel; a test checks every script.

## Restore

`bun run provision:traces --restore-snapshot <name>` closes ports 80 and 443 at the cloud firewall (proved from the read-back), creates a volume `traces-data-restore-<YYYYMMDD>-<HHMM>` from the snapshot (with the description `restore-of:<snapshot name>`), stops Docker, detaches the one attached `traces-data*` volume, attaches the new one, then probes, mounts and verifies the sentinel. It stops there with Docker stopped and the ports closed; the old volume is kept, detached.

- **DigitalOcean's volume listing lags a completed action.** The first real restore failed because the single listing read right after `detach --wait` still showed the droplet. A new volume, an attach and a detach are all read back from the listing for up to `VOLUME_LIST_ATTEMPTS` reads, `VOLUME_LIST_INTERVAL_MS` apart (one shared poll, `pollVolumeListing`), before the step is called failed.
- **The restore volume's description is a label, nothing more.** It is created with `--desc restore-of:<snapshot name>` so a person reading `doctl compute volume list` sees where it came from. No code reads it back to decide anything; `restoreDescription` only refuses, before any change, a name it could not write whole (1 to 128 letters, digits, dots, dashes and underscores). `listVolumes` reads `doctl compute volume list --output json`, not the text table, so the description (free text) is a field and not a column to split, and it is shown, with the volume's state, in the refusal messages. The restore also reads the clock once and uses that one stamp for the volume name, the quarantine directory and the report.
- **The "old" volume is whichever `traces-data*` volume is attached.** After a restore that is itself a `traces-data-restore-*` volume, and no volume named exactly `traces-data` need exist. A first run (one attached volume) creates a new restore volume, detaches the attached one, names it in the closing message whatever its name, and never touches a detached restore volume left by an earlier restore.
- **The run needs exactly one attached `traces-data*` volume, and nothing else is continued.** Any other count (none attached, or more than one) stops it after the ports are closed and before any volume is created or changed. The message gives the count, says the ports stay closed and no volume was changed, and lists every `traces-data*` volume by name, state (attached to this droplet, detached, attached to another droplet) and description label. A detached restore volume left beside the one attached volume is ignored.
- **Recovering an interrupted restore is a hand step.** A restore that stopped after the detach and before the attach leaves nothing attached, Docker stopped, and the previous volume and the new restore volume both detached. The run cannot tell which detached volume held the live data, so you choose:
  1. Identify the volume that was live before the restore started (the previous `traces-data*` volume; `doctl compute volume list` shows names and labels).
  2. Attach it by hand: `doctl compute volume-action attach <volume-id> <droplet-id> --wait` (the refusal prints the droplet ID).
  3. Run the same `--restore-snapshot` command again from the start. The quiesce step copes with Docker already stopped and nothing mounted. It creates a fresh restore volume, so the leftover one stays as it is.
  4. Delete nothing. A leftover restore volume, and the previous volume, can be deleted only after a restore is proven.
- **After a failed attach or detach,** the message says which volume is where as far as the run knows, with Docker stopped and the ports closed. It gives the same hand step: get the previous volume attached (check `doctl compute volume list` first), then run the restore again from the start.
- **Not covered:** a restore that failed after the attach (probe, mount or sentinel) leaves the restore volume attached, so a rerun sees one attached `traces-data*` volume and starts a new restore from it as the "old" one. Verify by hand instead of rerunning. A failed Tempo block scan (the next bullet) is the same case: the volume is attached and mounted, so do not run the restore again.
- **A snapshot is taken while the stack runs, and Tempo's local storage can be caught mid-write.** ClickHouse, PostgreSQL and the object store came back complete in the rehearsal. Tempo's did not: the snapshot caught a block its compactor had just written whose data had not reached the disk, so on the restored volume that block directory held only zero-byte files. One empty `meta.json` makes Tempo's tenant index fail, and Tempo then serves no stored block at all.
- **The restore quarantines torn Tempo blocks.** After the restored volume is mounted and its sentinel verified, and while Docker is still stopped, one more host step (`tempoQuarantineScript`) scans `blocks/<tenant>/<block-uuid>/` under Tempo's data (the Docker volume `traces_tempo_data`, `TRACES_TEMPO_DATA_DIR`) and moves each torn block to `/mnt/traces/tempo-quarantine/<YYYYMMDD-HHMM>/<tenant>/<block-uuid>`. Torn means a block directory with a `meta.json`, or a `meta.compacted.json`, that is empty or is not a JSON object. A directory with neither file is left alone, as are plain files (`work.json`, `index.json.gz`, `index.pb.zst`) and anything not named like a UUID. "A JSON object" is checked as first and last non-space byte `{` and `}`, not parsed: no script here relies on `python3`. The move is a rename on the same filesystem (never a copy, never a delete), the step is idempotent, a snapshot from before Tempo wrote anything is "nothing to do", and every restore runs it. The restore logs the count and each tenant and block. A scan that fails stops the restore with the host's state in the message.
- **The limit: Tempo can then be missing recent traces.** A quarantined block replaced inputs the compactor had already marked `meta.compacted.json`, and nothing revives those, so Tempo can lack whatever its most recent compaction covered. In the rehearsal on 2026-11-21 that was 37 minutes of a 3.6-hour history: 31 of 40 canary traces came back in Tempo and 40 of 40 in Langfuse. Langfuse is the complete record. Nothing prunes the quarantine directory and Tempo's retention does not reach it: look at it, then delete it by hand.
- **Proven on the real host on 2026-11-21:** the rehearsal completed, but through a resume path that has since been removed, so it does not prove the current code. Docker starting on a restored volume and `traces sender revoke --all` were also proven. The current first-run path, with its polling, has not completed a real restore end to end: its detach, attach, mount, sentinel, quarantine-scan (with nothing to move; its move path has not run on the host) and reopen steps each ran on the host, but the polling and the JSON volume listing shape were checked only against the real CLI's output, never in a whole restore. The quarantine step is also tested against real files in a scratch directory and through the simulated host.

## Known outbound calls

Telemetry is off wherever a setting exists. Langfuse web contacts `langfuse.com` for an update check when the UI loads (no setting), and the browser fetches two badge and asset hosts. Grafana makes no outbound call with the plugin pre-installer, update checks, Gravatar and the news feed off, except the alert notifications: a firing or resolved alert posts to the Discord webhook, with fixed text, the rule name, labels and numbers. Prometheus makes none.

## Proven only on the real host

The deploy tests run the generated scripts through a simulated host and parse every one with `bash -n`; the token script also runs for real against a scratch directory. Some behaviours can only be proven on the host.

The first deploy ran these on the real host and they held: the `mc ilm rule` commands inside the MinIO image, `clickhouse-client` with the container's own password, the bootstrap probe inside the Langfuse web container (401 for the deleted key), the collector image digest read-back, the queue-volume owner, the deploy marker and both locks taken with no other holder, the failure handler leaving the route held, the token-file creation script, and the reporter's read of a real Langfuse row and raw batch.

The first deploy also found five defects that no test had caught, each now pinned by a test: a directory mounted over ClickHouse's `config.d` hid the image's own listen file, so ClickHouse answered its healthcheck and refused every other container; Langfuse binds to `HOSTNAME`, which Docker sets to the container name, so loopback probes were refused until `HOSTNAME=0.0.0.0`; `system.tables.create_table_query` is one line, so a TTL parser that looked for a `TTL` line found none; Tempo creates its directories with mode 0700, so the reporter has to run as Tempo's user; and Tempo keeps `work.json` beside its tenant directories, so the block listing must enter directories only.

Still unproven on the host: Prometheus starting on a fresh volume owned by 65534, its scrape of all four targets, Grafana loading the alerting files with the real webhook, a rule evaluating against real series, a notification arriving in Discord (and its silence in the UI), `grafana-alerting` against the live provisioning API, and `/healthz` failing with Grafana down. Also: two deploys overlapping (the step lock's wait and the overtaken exit), a hold or open racing a deploy, whether `docker compose config --hash <service>` equals the container's `com.docker.compose.config-hash` label (if not, the deploy only ever holds more, never less), `traces ingest open`, the sender token add script (`revoke --all` ran for real on 2026-11-21), and the byte limiter under load. A restore is no longer on this list: see the Restore section for what ran on 2026-11-21.
